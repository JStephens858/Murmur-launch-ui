## 2026-10-07 — Account creation on the web
**Decision:** `/signup` creates accounts: email, password and confirmation (the app's rules: 8+ characters, an uppercase letter, a lowercase letter, a number), sent to a Server Action. The API owns creation through one public mutation, `createUserWithPassword(email, password)` returning the usual envelope (errorCode 409 email in use, 422 password policy, 400 bad email, 429 rate-limited), which makes the Auth0 email/password user and the `users` row together. The API returns no tokens; the web then signs in exactly as `/login` does and writes its own session. The person's address goes to the API as `X-Murmur-Client-IP` for per-person rate limiting. After sign-up the user goes through onboarding on the site, as in the app (next piece of work; for now they land on `/account`). `/login` links to `/signup`.
**Why:** Josh wants web sign-up, with onboarding (where physician verification happens) on the site. Creation in the API keeps the Auth0 user and the database row consistent in one place for every client. Tokens stay with the web's own Auth0 client because refresh tokens belong to the client that requested them; tokens minted elsewhere couldn't be refreshed by the web's session. Doing the token steps in the browser was ruled out: the web's sign-in uses its client secret, and tokens live only in the encrypted HttpOnly session cookie.
**To watch:** the mutation is public, so rate limiting and any CAPTCHA belong in the API; the password must stay out of the API's request logging; the "email in use" message stays soft so the form can't list members.
**Status:** Built but switched off (2026-10-09): live only where `ENABLE_WEB_SIGNUP=true`; otherwise `/signup` is a 404, the action refuses and `/login` points to the app. Supersedes the "accounts only in the iOS app" reasoning of 2026-08-11 once switched on (the custom sign-in itself stands).

## 2026-10-05 — Post composer, ported from the app's PostCreationView
**Decision:** `/compose/post` is a one-screen composer like the app's: a post is an ordered list of items (text, photo, video, file, poll) under a settings card, with a bottom toolbar (Text, Library, Camera on touch devices, File, Poll). `?group=` starts in a group, `?quote=` makes a follow-up, `?edit=` edits; the post page shows Edit and "Post follow-up" to whoever the app shows them to. Publishing is the app's sequence: images re-encoded to JPEG (2100 px, q 0.7), MD5 of every file, one `getUploadFileUrls`, then one `createPost`; the tus uploads start only after that, with the fileKey, postId and mediaElementId in the metadata. The composer then returns to where it came from, and an "Uploading… / Processing…" card at the top of the feed and of the group polls `getPostUploadStatus` every 5 s until the server publishes, then puts the post at the top of its group and, if followed, the feed. Uploads live at module level so they survive navigating around the portal; closing the tab ends them (a beforeunload prompt warns), leaving the post unpublished on the server as killing the app does. One draft per mode (new, quote of X, edit of X) autosaves to IndexedDB, media included, and is restored with a "Discard draft" action. Extras follow the app's rules: anonymous posting, category picker plus moderators' "Additional categories", "Use as title" (sent as `indexInPost: -1`), admins' poster frame (`previewImagePercent`), "Post as", moderators' clone-a-post link, and content creators' bounties.
**Why:** The user asked for the app's flow with all item types and extras. Uploading after createPost is how the backend ties files to elements, so the feed card (the app's UploadingFilesView) is the only way not to block the author.
**Differences from the app:** moderator rights come from `getMyModeratorStatus` up front (the app only learns them when Group Info is opened, so its clone and category tools rarely show); the category default is a key that exists (the app can send "default" when no such category exists); deleted poll options are actually dropped (the app still sends them); a link preview can be closed. **Not ported:** image and video cropping, Remove Audio, on-device transcription, video re-compression, PDF thumbnails (attachments get a thumbnail only when they are images), multiple named drafts, and the full reply screen (comments keep their inline box). Videos go up in their own container type (e.g. video/webm, video/quicktime) rather than always video/mp4. Verified against the mock, which now answers the composer's calls.
**Status:** Active

## 2026-10-02 — Experience tab and editor, ported from the app's ProfileExperienceView2
**Decision:** The profile's Experience tab and a new `/profile/experience` editor page follow the app's current design, not the older column-per-field CV. Items are grouped into the app's sections in its order (Education, Training, Areas of focus, Practice, Hospital affiliation, Other, with Organizations last); areas of focus render as chips, everything else as a card with the type as a kicker, the title, the description and a year range ("2014 – Present"). The profile shows only populated sections plus an Edit button on your own; the editor shows every section with an Add button, a dashed "Nothing here yet" row, and for chips a dashed Add chip and an in-place remove. Add and edit happen in a dialog (the app's sheet): a capsule type picker when the section has more than one type, the per-type primary and secondary labels and placeholders copied from the app's `fieldSpec`, start and end years, and an "I'm still here / current" checkbox that blanks the end year. The editor writes only title, description, start, end and isCurrent, as the app's `makeCVItemIn` does; the older practiceType, discipline, companyName and location columns are still read and shown as a fallback second line on legacy rows but never written. Every change sends the **whole list** to `setCVItemsForUser`, which replaces the user's items, renumbered from 1 with the new item appended and given no id (the backend mints one), exactly as the app's `saveEditingCv` builds it; the response replaces the cached list. Type display names come from `getCVItemTypes` with the app's fallback table until they load.
**Why:** The app rewrote this feature recently and this is what physicians see there; the web's old grouped list used names and fields the app no longer writes. Replace-all is the backend's only write path for CV items.
**Not ported:** the experience quiz (colleague verification), which is a separate feature with its own queries. Verified against the mock, which now holds a mutable CV list, item types and the replace-all mutation.
**Status:** Active

## 2026-10-02 — Edit Profile: the app's fields and calls, photo via the app's tus upload
**Decision:** `/profile/edit` ports the app's EditProfileView. The fields are the app's, in its order: username (a-z, 0-9, _; lowercased and filtered as typed), first name, last name, location, specialty, NPI, disclosures, interests, bio, post flair, plus the profile photo. Save is enabled only when something changed, as in the app. Text goes through `updateUser`, the mutation the app sends, but **only the changed fields are sent**: the backend treats a null argument as "leave it", an empty string as "clear it", and re-runs NPI validation whenever an NPI arrives, so resending unchanged values is not free (the app resends everything). Error 504 is the backend's "duplicate username" and is reworded for the form. The photo follows the app's protocol exactly: re-encode as JPEG (quality 0.7 like the app's `jpegData`, longest edge capped at 1200px), MD5 it, ask `getUploadFileUrls` for a `profileImage` slot, then tus-upload the bytes (`tus-js-client`, `spark-md5`) to the returned `v1.uploads.murmurmd.com/files/…?sig=` URL with the bare API token in `authorization`, as the app does. The upload server reports completion to the API, which writes the thumbnail and medium URLs onto the user, so after the upload the page re-reads the profile every two seconds (up to six times) until the URL changes, then returns to `/profile`.
**Not verified against the real upload server:** the mock stands in for both the API and the tus endpoint. The real `v1.uploads.murmurmd.com` must allow browser CORS (POST, PATCH, HEAD with the tus headers, and expose `Location` and `Upload-Offset`) for the photo to work from the web; the iOS app never needed that. Text editing has no such dependency. Fields the app can set elsewhere (medical school, country code, TOS, phone, claimed user class) are not on this form, as they are not on the app's edit form either; the cover photo and profile link are not editable in the app and stay read-only here.
**Status:** Active

## 2026-10-01 — Two share cards, and every public page sets its own OpenGraph block
**Decision:** Social-share images are two committed PNGs rendered by `npm run og-images` (`scripts/og-images.mjs`, Next's own ImageResponse over the dark-theme tokens, the dark wordmark, and Inter fetched from Google Fonts at run time): `og-default.png` for the site and `og-invite.png` for the `/invite` and `/invite4` landing pages. Every public page spreads `shareMetadata(path, card)` from `lib/metadata.ts` into its metadata export; the helper sets type, locale, og:url, siteName, the card image and the X handle, and deliberately leaves title and description out so Next fills them from the page's own `title` (template applied) and `description`.
**Why:** `public/og.jpg` was still the Launch UI "Landing Page Kit" promo image (4800×2520, 3.4 MB, declared 1200×630), so every shared link showed a React/shadcn template card. Separately, Next merges metadata shallowly: a page that sets only `title` and `description` inherits the root layout's whole `openGraph` block, so About, Physicians, Partners, Get the App and Videos all shared the home page's OG title, description and URL while their own descriptions never reached the card. Invite links shared by text now show an invitation card rather than the generic one; the invite title is absolute so the suffix doesn't double the brand.
**Alternatives considered:** Next's `opengraph-image.tsx` file convention, which renders the card per route at build or request time. Ruled out for now: the invite routes are catch-alls, which complicates the image route, and static PNGs keep the production build free of a font fetch. Per-page cards with the page title drawn in were also possible; two cards is enough until there is something page-specific to show.
**Status:** Active

## 2026-09-23 — Explore: a chooser over the app's getExplorePostsForUser, with a hashtag chip
**Decision:** `/explore` is a chooser like the videos page's (All posts | Cases | Polls | Tips & Tricks | Journal | Question, the last two added 2026-09-24) over one post list, plus an optional hashtag chip tacked on the end of the row, applied by tapping a tag on any card and cleared from the chip. All of it is the app's `getExplorePostsForUser`, which is two queries behind one name. **Cases, Polls, Tips & Tricks, Journal and Question** ask for one section of the reader's nightly-computed explore list (`exploreSectionCounts`, the same argument ExploreView2 uses with 4/4/10; the nightly job also fills `journal` and `question`, which the app never shows), 10 at a time, paged by the section's last post id (`afterPostId`). **All posts** and **any hashtag** take the score path: no sections, `count`, and `maximumScore`/`maximumDate` as the cursor — the lowest score on the page and the oldest date among posts with that score, which is the app's `lowestScoreAndDate`. The score that matters differs: All posts is ranked by `baseUserPostScore` (post score weighted by the reader's interest in its hashtags), a hashtag list by `baseComputedPostScore`; both fields were added to the store fragment and only arrive on explore responses. A short page ends a scored list. Dates go as ISO 8601 UTC with the Z stripped, as the notifications cursor does.
**Hashtags disable the sections:** the backend's hashtag path ignores sections entirely, so applying a tag switches the chooser to All posts and greys the section choices (with a title explaining why); clearing the tag leaves All posts selected. Cases can't be filtered client-side (the flags aren't on the post), so this is honest rather than silently wrong.
**Section paging works around a backend quirk:** the section path has no end-of-list signal and throws (a TypeError in the resolver) when asked for more posts than remain, whether that's page one of a short section — a reader with six polls gets an error for `count: 10` — or the tail of a long one. The client retries a failed section page with half the count, each failure narrows a bound on how many can remain, and later pages ask for no more than that; a failure at count 1, or a bound of zero, is the end. Draining a section costs a few extra requests at its tail (the mock's 13 tips took 6 requests), each logging a stack on the backend. The right fix is in Murmur-apollo: return what remains and an `endOfList`. The app never hits this because its `fetchMorePosts` is commented out; it shows only the first page of each explore list.
**Trending hashtags (2026-09-25):** the app's TrendingHashtagsView is a "Trending hashtags" heading over wrapped chips from `getTrendingHashtags` (the ten tags whose posts from the last 25 days have the highest summed score, the same for every reader; the rows land in the store and are refetched after five minutes). Here it sits between the chooser and the list rather than at the foot of the page, since the web page is one list, not the app's stack of sections. Tapping a chip applies it as the page's hashtag filter, which is what the app's push to the hashtag post list amounts to; the active one is highlighted, tapping it again clears the filter, and the strip stays visible while a tag is active so the reader can hop between trending tags. Hidden while loading or when empty, as the app hides it. Note the app's `loadTrendingHashtags()` call is commented out in ExploreView2's onAppear, so the strip never actually appears in the shipped app; the query still works.
**Shared list:** the feed's post list became `InfinitePostList` (any infinite query of post-id pages), which the feed, groups and Explore all render; `PostCard` gained an optional hashtag-click handler, and its chips become buttons only when one is passed. **Not built:** the app's interest picker and group teasers on Explore; the URL carries the tag (`/explore?hashtagId=…&hashtag=…`, added 2026-10-02 so hashtag chips on the feed and the post page can link here with the tag applied; the URL is the source of truth and toggling a tag on Explore replaces it) but not the chooser choice. Verified against the mock (which now answers `getExplorePostsForUser`, throwing past the end as the real backend does), not the real API: the score cursor's date handling and the section error's exact message are worth a look on real data.
**Status:** Active

## 2026-09-18 — Profile follows the app's ProfileView2: one screen for yourself and for others
**Decision:** `/profile` is your own profile and `/profile/<userId>` anyone's (your own id there renders the own variant). It's one screen, as in the app: the difference is only in affordances — your own gets "Edit Profile" (a placeholder page for now; the app's EditProfileView / `updateUser` isn't ported) and someone else's gets Follow/Following and, when the viewer is a doctor and the profile isn't the anonymous author, a message button that creates or reuses the conversation and opens it. Everything else is shared: avatar, name, @username, specialty, link, location, "Joined Mon YYYY", "Invited by: @x"; the Profile | Experience tabs; on Profile the Disclosures / Interests / Bio blocks ("No profile information added yet" when empty), the Post Likes / Best Answers / Posts of the Week counters from `getUserProfileCounters`, and the Posts (N) | Bookmarks (N) | Following (N) | Followers (N) lists; on Experience the CV items from `getCVItemsForUser` grouped by type, with the app's two empty-state texts.
**Data:** the person is whatever the store holds, fetched with `getUsers` when missing (the app has no per-profile query either); the store fragment now selects the app's full PublicUser field list. Followers and following come from `getFollowers` as ids, with the people fetched separately since the store payload may not include them. Posts and bookmarks page 10 at a time by `beforeDate` (the oldest post's date), as the app does with its date cursor. Follow state is whether the target is in your own following list; `followUser(userId, follow)` is flipped optimistically in both lists and, unlike the app, put back on failure. Post cards and the post page now link the author to their profile.
**Deliberately not shown, matching the app:** cover image, rank/score/progress, employee and verified badges — all fetched, none displayed on iOS. **Not built:** editing, the own-profile settings sheet (address-book sync, interests, delete account), the block/report the app doesn't have either. A deleted account renders a short notice. Verified against the mock only.
**Status:** Active

## 2026-09-17 — Direct messages follow the app's DirectMessagesView, ConversationView and CreateDMGroupModel
**Decision:** `/messages` lists conversations from `getDMGroupsForUser2`, sorted by their last message's date; a row shows an unread dot (the app's binary dot, not a count), the app's computed title (first names of the other members, "a, b & c", cut at ~35 characters with "& N more", "Just you so far" when alone — conversations have no stored name), the age, and the preview: "You said:" / "<Name> said:" with the text, "<Name> posted an image/a video", or "Nothing yet...". A conversation (`/messages/<id>`) is `getPostsInDMGroup`, 20 a page by last post id, newest first and rendered oldest-at-top in its own scroll area pinned to the bottom, older pages fetched when the reader scrolls to the top (the server's cursor page repeats the cursor post, so ids are deduped). Bubbles: mine right, others left; in group chats the sender's name above the first of a run and their avatar beside the last; a date line when the gap exceeds two hours; the time on hover (the app reveals it with a drag). A members strip in the header (linking to participants for doctors, as the app gates it).
**Sending** is `createPost` into the conversation with one text media element — the backend routes direct-message groups to its own handler, and its dedicated `createDMPost` mutation isn't exposed to the app either. Enter sends, Shift+Enter breaks a line. Text only for now; the app also attaches one image or video per message through the upload-URL flow, which isn't built.
**New conversation** (`/messages/new`, "New Group Chat"): pick people from followers ∪ following or a search from three characters (`searchUsersForText` with the feed group id, `@` and smart quotes stripped, the app's "N people match" / "No search results found" copy), write the first message, Send → `createPostGroup(direct_message, memberUserIds)` — the backend returns the existing conversation for the same member set — then the message, then the compose page is replaced by the conversation. **Participants** (`/messages/<id>/members`, "Group Participants"): remove with the app's "Confirm Removal" dialog (removing yourself is how you leave), and an "Add Members" sheet with the same picker.
**Read state and freshness:** `setLastSeenForPostGroup(now)` fires when a conversation opens and again when it's left, then the badge sources refetch; the app fires it only from its back button. The app receives new messages over a subscription; here the newest page refetches every 15 seconds and on focus, and the list every 30 seconds.
**Not built:** attachments, message deletion/reporting (the app has none either), the profile-page envelope entry point (profiles aren't built), live delivery over the subscription. Verified against the mock only.
**Status:** Active

## 2026-09-15 — Groups follow the app's GroupListView, PostListView and PostGroupDetailsView
**Decision:** `/groups` lists every group from `getAllPostGroups` (the query the app actually uses; its `getPostGroupsForUser` document is dead code), sorted client-side subscribed-first then by name, direct-message groups dropped, under the app's own headings ("You're subscribed to these groups:" / "Other groups you might be interested in:"). Rows show the icon (a URL, a single emoji, or the logo), name, "Private group" with a lock, the sponsor line with a megaphone, member count only when the reader can enter, and the Join / Request Access button; a private group the reader can't enter isn't tappable. Access rules are the app's, evaluated client-side from `groupType`, `subscribed` and the `restrictions` JSON against the reader's `userClass` (now on the profile query, with `isAdmin`).
**Group page** (`/groups/<id>`) is the same post list as the feed with the group's id and the selected category, plus: a members strip (linking to `/groups/<id>/members` for doctors only, as the app gates it), a Group Details link, a Post button when `canPost`, category tabs for header-style and top-level browser categories, the pinned post above the list, and the app's join prompt when not subscribed. A browser category shows its child categories as cards and drills in with a "Back to <parent>" breadcrumb. **Details** (`/groups/<id>/details`) has the long-form Join/Leave (Leave only here and only when `canLeave`, no confirmation, as in the app), the "Watch this Group" toggle backed by `get/setPostGroupPreferences` (watching is a notification preference independent of membership; the app never uses `watchPostGroup`), and the visible moderators. **Members** pages 30 at a time by offset.
**Membership** is optimistic and rolled back on failure; join and leave both drop the cached feed, since the app resets its feed model on either. **Request Access** is a dialog with the app's copy, sending `requestAccessToPostGroup(message)`, then "Message sent" with the app's follow-up text. One small departure: after joining, the list refetches and re-sorts, so the group moves to the subscribed section at once; the app leaves it in place until the next fetch.
**Not built:** moderators' membership-request review, follow buttons on member rows, per-category card styles (`displayStyle`: video, journal, reference — all render as the standard card), the post-filter highlighting, and sub-group cells. Verified against the mock only.
**Status:** Active

## 2026-09-15 — Post videos autoplay by visibility, one at a time
**Decision:** On the post page, inline videos (the post's and its comments') are driven by a page-level coordinator (`lib/portal/autoplay.ts`): a shared IntersectionObserver reports how much of each video is on screen, the most-visible one that is at least half showing plays, everything else pauses, and nothing plays while the tab is hidden. Autoplay is muted because browsers refuse unmuted autoplay without a gesture; once the reader unmutes any video, later autoplays try unmuted first and fall back to muted. A video the reader paused stays paused until they play it again; a video they start pauses the others. A pause event with no decoded frame behind it (a stalled or failed source, which also fires `pause`) is not treated as the reader's choice, so a network hiccup can't permanently exclude a video. `VideoPlayer` gained a shared `ref` so callers can reach its element.
**Verified** with the mock: the coordinator selects videos 1 → 2 → 3 → 1 as the page scrolls. Real playback and the pause-of-the-previous-video path could not be exercised because the mock's streams are fakes; worth a look on real posts.
**Status:** Active

## 2026-09-15 — Poll media element follows the app's PollView
**Decision:** Polls on the post page work as in the app. The question is the element's `mediaText`; the options are the JSON array in its `properties` (`{id, text, height}`, `height` ignored), in authoring order. Counts and the reader's own choice come from `getPollResults`, fetched once when the poll appears; voting is `selectPollOption`, whose response carries the new counts. Before choosing, the reader sees one outlined button per option plus "Just show the Results", which votes the null UUID: the backend's results query excludes that id from the counts, so it reveals the tallies without adding to them. After choosing: a bar per option with a truncated percentage (all tied leaders highlighted as winners, zero-vote options shown at 0%), a check on the reader's own choice, "N votes", and the app's "* Poll responses are anonymous" note. Votes can't be changed; there is no expiry or minimum-votes rule. Two small departures: a skeleton stands in until the results query settles rather than briefly showing buttons to someone who has already voted, and a failed vote puts the buttons back (the app leaves the optimistic state).
**Store shape:** the normal store never carries compiled `pollResults`, so the page ignores that field; `properties` was added to the portal's store fragment. The feed card's "Take the poll" hint now keys off a poll media element being present, as the app's `hasAPollQuestion` does, rather than a guessed category key — so it appears once the card's prefetch has hydrated the post. It carries the app's `text.badge.checkmark` glyph (2026-09-18).
**Icon set (2026-09-18):** every SF Symbol the app references is now exported into `components/portal/icons.tsx` (161 icons) from `scripts/sf-symbols/app-symbols.txt`, so later work picks from the module instead of exporting one at a time; the exporter skips names this macOS lacks and reports them.
**Status:** Active

## 2026-09-15 — Portal Videos reuses the public browser; the player grows like, comments and Full Post when signed in

The browser gained three props for this — a `source` for pages (default: the public `/api/videos` route), a `postHref` that turns the player's title into a link, and a `renderActions` slot under the metadata — so the public page is unchanged in behaviour. ## 2026-09-15 — Notifications tab mirrors the app: server-composed rows, seen-on-refresh, Clear all
**Decision:** `/notifications` is built from `getNotifications2` exactly as the iOS app's NotificationsView is: pages of 20 keyed by `beforeDate` (first page far-future, then the oldest row's date), the row text is the server's `notificationText` with no client templates, the avatar is the server-joined `notificationImageUrl`, and each row wears the app's per-kind SF Symbol as a small badge (`IconPicker.notificationType`, exported through `scripts/sf-symbols`). **Decision:** `/login` collects email and password on our own page, calls Auth0's token endpoint directly with the Resource Owner Password grant (`password-realm`), and writes the result into the `@auth0/nextjs-auth0` session cookie. The Auth0-hosted login page is no longer used for physicians. `/auth/logout` and the rest of the SDK's routes are untouched.

## 2026-08-10 — `/post/<id>` is server-rendered, with the `mc` cookie deciding how much shows
**Decision:** `/post/<postId>?mc=…` renders in Next rather than injecting tags into the old React shell. `generateMetadata` produces the OG/Twitter card; the page renders the post itself — creator, group, date, and media elements in `indexInPost` order, covering text, image, video (HLS via the existing `VideoPlayer`), poll (with result bars) and file.
**Why the page has two shapes:** the backend's `resultType` decides. With a matching `mc` it returns `"full"` — everything. Without one it returns `"og"`, which it describes as "used for opengraph only": a 100-character excerpt, a preview image and a username, no media, and **`createdDate` set to now rather than the post's real date** — which is why the ungated view deliberately prints no date. `"none"` (unknown, deleted or unpublished post) becomes a 404.
**Details that matter:**
- `og:url` is the bare `/post/<id>` path. The magic cookie must never travel in metadata that gets shared; legacy got this right by splitting the query off first, and the suite now asserts it.
- Title and description both use legacy's `truncateString(postText, 100)`, so previews already cached by Slack and X don't shift. `Logo-registered-whitebg.png` was copied into `public/` for the same reason — it's the fallback card art on posts with no preview image.
- Never cached (`force-dynamic`): a cached render could serve one visitor's gated view to another.
- Post media uses plain `<img>`, not `next/image`. The media hosts are user-generated — mostly the company's S3 bucket, but there are `pbs.twimg.com` URLs in the table — and `next/image` throws on any host missing from `remotePatterns`, which would turn one unusual post into a broken page.
**All four URL forms in circulation are accepted**, via `parsePostRef` in `lib/legacy-urls.ts` and a catch-all route segment:
```
/post/<dashed-uuid>?mc=<cookie>      /post/<dashed-uuid>/<cookie>
/post/<flat-uuid>/<cookie>           /post/<flat-uuid>
```
The flat id is the app's form — dashes stripped — and the cookie may arrive as a second path segment rather than a query parameter. All four were confirmed working against live `murmurmd.com` before porting. A cookie in the path wins over `?mc=`; the two come from different clients and never co-occur.
**The id has to be re-dashed before it reaches the API.** `murmur-uuid-buffer.toBuffer` throws on anything that isn't exactly 36 characters with dashes, so a flat id cannot be passed through — `parsePostRef` normalises it. Mis-parsing is safe: the backend compares the cookie for equality, so a wrong cookie degrades to the excerpt-only `"og"` response rather than granting anything, and an unparseable id fails the query outright. Junk in the cookie position 404s rather than silently rendering a teaser that looks like the cookie merely failed to match.
**Not supported:** the concatenated form `/post/<flat-uuid><cookie>` with no separator. Live returns 200 with an empty `og:title` and the generic logo for it, so it isn't a real shape and inventing support would be guesswork.
**`og:url` is always the canonical dashed, cookie-free path**, whichever form the visitor arrived on — so the flat form doesn't create a second address for the same post, and the cookie can't be republished by a crawler. (The cookie does appear in Next's RSC router payload, a script in the body, but that is only sent to the client that supplied it in the first place, and never reaches the document head.)
**A trap worth remembering:** `/post/` is deliberately **not** in `robots.txt`. Slackbot, Twitterbot and facebookexternalhit all honour robots.txt, so disallowing it would stop them fetching and break the link previews these pages exist to produce. Keeping them out of search is done with `robots: { index: false }` in metadata, which suppresses indexing without blocking the fetch.
**Status:** Active

## 2026-08-06 — Fire-and-forget gets two different answers

## 2026-08-06 — A method guard in proxy.ts, because Next aliases HEAD to GET
**Decision:** `proxy.ts` answers any non-GET request to a legacy action path with a bare 200 before anything else runs. `lib/legacy-guard.ts` additionally skips the mutation (while still rendering the page) on prefetch headers, known crawler/scanner user-agents, and a repeat of the identical URL inside a 10-minute window, logging one structured line per hit.
**Why:** Next implements `HEAD` by calling the `GET` handler verbatim (`next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js`), and a Server Component cannot see the request method at all — so the proxy is the only place this check can live. Without it a link-checker's HEAD probe sets an admin flag. Beyond that, `/doNotPromote` and `/acceptReengagementPosts` change state from an unauthenticated GET, and Outlook Safe Links, mail gateways and browser prefetch all issue GETs; `/acceptReengagementPosts` has no secret in its URL at all, just a date and a username.
**Deliberately not done:** a confirmation interstitial, the only complete fix, because it would change the one-click behaviour of links already in the wild. The UA list and prefetch headers are spoofable — this reduces accidents, not attacks.
**Not applied to invite linkage:** legacy counted every view including crawler fetches, so filtering them would shift the attribution baseline mid-stream.
**Status:** Active

## 2026-08-06 — AASA is a route handler reached by rewrite; the rewrites live in proxy.ts
**Decision:** `/.well-known/apple-app-site-association` and `/apple-app-site-association` both rewrite to `app/api/aasa/route.ts`, which sets `Content-Type: application/json` explicitly. `/health-check*` and the extensionless `/info/*` URLs are rewritten in `proxy.ts` too, not in `next.config.mjs`.
**Why:** The AASA filename has no extension, so serving it from `public/` would guess `application/octet-stream` where Apple requires JSON — and Apple will not follow a redirect, so it must be a rewrite. Handling all three in `proxy.ts` avoids depending on the relative ordering of middleware and `beforeFiles`, and gives `/health-check-<service>` the intra-segment prefix match no App Router pattern can express. Both AASA URLs now serve valid JSON, which incidentally fixes the malformed root copy on the old box (three missing commas). Superseded on the `/app/*` question — see the 2026-08-10 entry.
**Gotcha found in verification:** query strings do **not** survive `NextResponse.rewrite`, so the health service had to move into the rewrite's path (`/api/health-check/<service>`). With `?service=` every probe silently reported on the default service.
**Status:** Active

## 2026-08-11 — Custom email/password sign-in instead of Universal Login
**Decision:** `/login` collects email and password on our own page, calls Auth0's token endpoint directly with the Resource Owner Password grant (`password-realm`), and writes the result into the `@auth0/nextjs-auth0` session cookie. The Auth0-hosted login page is no longer used for physicians. `/auth/logout` and the rest of the SDK's routes are untouched.
**Why:** Accounts must be creatable only in the iOS app, where physician verification happens, and never on the web. Owning the page means the web can never render a signup affordance.
**Alternatives considered:** Keep Universal Login and switch off "Sign Ups" on the database connection (Auth0 → Authentication → Database → Disable Sign Ups). That is one dashboard toggle, no code, and keeps Auth0's brute-force protection, MFA, bot detection and password-reset flows on the path they were designed for. It was not taken because we wanted the login page under our own design and control — this entry exists so the trade is a decision on record rather than an accident.
**Consequences to watch:**
- We now handle physician passwords in our own process. They are never logged and never stored, but the attack surface is ours.
- MFA cannot be completed in this flow. If anyone enrols, `mfa_required` comes back and `/login` tells them to use the app. Handling it on the web means implementing the `mfa_required` challenge exchange.
- The Password grant must stay enabled on the Auth0 application. It is disabled by default and OAuth 2.1 drops it; a future Auth0 change here breaks web sign-in.
- Auth0's brute-force protection keys off the caller's IP, which is our server unless the `auth0-forwarded-for` header is right. `lib/auth0-password-login.ts` sends it from `trustedClientIp()`, so `MURMUR_XFF_TRUSTED_HOPS` has to be correct on the server or protection lands on the wrong address.
- There is no password reset or email verification path on the web yet.
- `lib/auth0-session.ts` reaches into the SDK's private `sessionStore` to create a session from tokens we already hold; the SDK exposes no public equivalent. It throws loudly if that internal shape changes on upgrade.
**Status:** Active, except its reasoning that accounts are made only in the iOS app: superseded by 2026-10-07 (Account creation on the web).

## 2026-07-07 — Background knot animation capped at 15fps and CSS resolution
**Decision:** `BackgroundLines` throttles its rAF loop to ~15fps and renders the canvas at CSS pixels (DPR 1) instead of Retina (DPR ≤ 2).
**Why:** At full refresh rate + 2x DPR, the full-viewport canvas re-uploaded ~15M pixels per frame to the GPU; a dev tab left open pinned Firefox's GPU process at ~100% CPU and saturated macOS WindowServer, freezing Josh's machine. The knot rotates once per ~2.5 min, so 15fps is visually identical; the strokes sit at 6-8% alpha, so sub-Retina resolution is imperceptible.
**Alternatives considered:** Pausing on `visibilitychange` alone — insufficient, since the cost is incurred whenever the tab is visible, not just when hidden (browsers already suspend rAF in hidden tabs).
**Status:** Active
